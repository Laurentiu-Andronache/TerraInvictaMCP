# TerraInvictaMCP wire protocol (in-game DLL)

This DLL mod is loaded by Unity Mod Manager (UMM). It uses Harmony to patch
game methods at runtime. It runs a localhost TCP server -- the
bridge -- inside Terra Invicta. External tools like AI agents or scripts
speak the protocol -- Claude Code, OpenCode, Antigravity, or plain netcat.
They can drive a running campaign, issue commands, read game state as JSON,
and control time without the GUI. A verb is one named request the bridge answers.

This document describes the contract shipped with mod version 0.1.0. Verbs
added after that carry a "since <version>" note on their row.

## Design principles

- **Thin DLL.** The mod exposes simple verbs. Sequencing, judgment, and test
  logic live in the client scripts. A DLL change requires a game restart. A script
  change costs nothing.
- **Never crash the game.** Every command runs inside a catch-all block. Failures
  return an error response. A broken bridge degrades to an inert mod.
- **Grow on demand.** New verbs are added only when a task cannot be done
  with existing ones. Unknown commands return an error. Clients can
  feature-detect against `version`.

## Transport and protocol

- TCP on `127.0.0.1:17470`. Localhost only, no auth. Anything on this machine
  already has the same user privileges. If the bind fails, log one line and
  run inert.
- Newline-delimited JSON (NDJSON: one JSON object per line), UTF-8. Request: `{"id": <int>, "cmd": "<verb>",
  "args": {...}}`. Response: `{"id": <int>, "ok": true, "data": ...}` or
  `{"id": <int>, "ok": false, "error": "<message>"}`.
- Multiple concurrent connections are accepted. All commands funnel into one
  FIFO queue. Each connection gets responses in the order it sent requests.
- A wire-contract change is a mod version bump. This is reported by `version` as
  `mod`. This document notes the version a verb appeared in.

## Execution model

- A background thread owns the socket to accept, read lines, and enqueue.
- Commands run on the main thread from the UMM `OnUpdate` callback. This
  survives scene reloads and save loads. The queue drains once per frame.
- Verbs must complete within a frame. Anything long-running is started by one
  verb, advanced by a per-frame tick, and observed by polling (see
  `time.run_until` and `combat.autoresolve`).
- With no campaign loaded, game verbs return `error: "no campaign"`. The verbs `ping`
  and `version` always work.

| `query.state` | `id` XOR `root`, `path?`, `include_private?` | reflection dump at depth 1 of whatever the arguments land on. Start from `id` (a registered game state) or `root` (a static entry point). Exactly one is required. `path` then walks from there. **Grammar:** identifier segments separated by dots. Each segment can optionally carry one `[n]` integer indexer applied to an `IList` or array -- `player.aiValues`, `currentSpeeds[2].displayName`. Dictionary keys are not addressable. Fields are tried before properties. A property getter runs game code. **A getter that mutates is the caller's risk**. The member dump invokes public getters too. A member re-declared with a narrower type in a subclass, as `template` is on `TIHabState`, `TISpaceBodyState`, `TILagrangePointState` and `TISpaceFleetState`, resolves to its most derived declaration. It does not fail on the ambiguity. Each step is guarded. A step that fails is an error naming the segment and the type it failed on (`no member 'aiValues' on TIPlayerState at segment 2`, or `at root segment 2` for a segment inside `root`, whose static member is segment 1 and whose trailing members continue from there). It does not return a silent null. A null answer and a wrong member name are otherwise indistinguishable. **`root`** is `TypeName.Member[.Member...]`. The type resolves against Assembly-CSharp first. A bare name is retried in `PavonisInteractive.TerraInvicta`. It then checks every loaded assembly, then does a by-name sweep. Results are cached, including misses. A namespace-qualified type name carries dots of its own. The longest prefix that resolves to a type wins. The rest are members. The first member is static. `root` without `path` is fine. **`include_private`** (default false) adds non-public instance members to both member lookup and the endpoint dump. It walks the base chain by hand because reflection does not inherit them. A private member whose name a public one already took is skipped. **Endpoint:** a game state answers `{id, type, name, members}` as before. A value the dump renders whole (string, enum, number, bool, date, template as its `dataName`, or an expandable list) answers `{type, value}`. Anything else answers `{type, members}`. Every response echoes `root` and `path`. **Members:** scalars verbatim, game-state refs collapsed to `{id, type, name}`. A list or single-dimension array expands when its declared element type is a game state, a template (each its `dataName`), a string, an enum (by name), or a number or bool. Anything else, including dictionaries and nested lists, stays a bare type name. This keeps one member from dragging in the rest of the graph. **Caps:** 16 dot-separated parts in `path` and in `root` alike. Both are refused on the split before anything is parsed or resolved. A root prefix that misses costs a sweep of every loaded assembly. The queue drains on the main thread. Expanded lists cut at 200 entries with no marker. |

| `spawn.fleet` | `faction`, `ships`, `location`, `design?` | builds `ships` (1-20) ships of one of the faction's designs. | `combat.start` | `attacker`, `defender`, `hab?` | `attacker.InitiateCombat(defender, hab, false)`. Returns `{started, queued, combat}`. One combat runs at a time globally. Nothing on this path checks hostility. Combat initialization keys one entry per faction with no duplicate guard. A faction on both sides throws inside the simulation tick every frame, and the strategy clock never runs again. |
| `combat.status` | | `{active, pending, blocked, autoresolve}`. Each combat carries id, participants (faction, AI flag, active-player flag, stance, bid), fleets, hab, and the `initialized` / `active` / `archived` / `autoresolve` / `autoresolving` flags. `blocked` mirrors `query.time`, so a client sees the combat freeze the strategy clock. `autoresolve` is the armed state of the verb below. |
| `combat.autoresolve` | `combat?`, `stance?` | arms a headless resolution and returns immediately. The client polls `combat.status`. Defaults to the active combat, else the first unresolved one. `stance` (Pursue, Defend or Evade) overrides the submitted player stance. It is checked against the stances the combat allows at submit time. Without it, the pick prefers Defend. |
| `fleet.bombard` | `fleet`, `target`, `altitude?` (`low`\|`med`\|`high`, default `low`) | orders orbital bombardment through `BombardOperation`, the engine's own fleet order, the way `AIDailyFactionPlanner.SingleFleetOperation` drives it: take the operation instance out of `OperationsManager.operationsLookup` (never a fresh one -- the interrupt check and the cancel path compare instances resolved out of that same dictionary), then `OnOperationConfirm(fleet, target, null, null)`. `altitude` picks among `BombardOperation_Low`/`_Med`/`_High`, whose only difference is the altitude passed to `InitiateBombardment` (`TIGlobalConfig` low/med/highBombardmentAltitude_km, 200/400/600 km shipped); closer is more damage per hit and more exposure to the target's defenses. No preconditions are bypassed. `ActorCanPerformOperation` runs first and its refusal becomes an error naming the states it read (`transferAssigned`, `dockedOrLanded`, the orbit body, `interfaceOrbit`, a synchronous orbit, `inCombatOrWaitingForCombat`, the fleet's `BombardmentValue`, the blocking operation, the possible-target count, `targetArchived`), then membership in `GetPossibleTargets`, whose refusal lists the targets that *are* possible. Two of its rules bite in practice: **a hab is only ever a target at a body other than Earth** -- at Earth the possible targets are regions, armies, space facilities, xenoforming, known alien facilities and UFO landings, never habs -- and a hab whose factions include a permanent ally of the bombarding faction, or which has no present modules, is filtered out; landed fleets at the same hab sites are targets on the same non-Earth branch. Confirming against a human nation's region commits an atrocity (`SpaceBombardHumanNationRegions`) before the bombardment starts -- permanent campaign state, flagged by `atrocityCommitted` in the return. Returns `{fleet, target, operation, atrocityCommitted, bombarding, bombardmentTarget, altitudeKm, endBombardmentReason, durationDays, completes, hab?}`, read back off the fleet; `hab` is present only when the target itself is a hab (a landed-fleet target's host hab is not the thing being bombarded) and carries `{underBombardment, okayModules, presentModules}`. **Bombardment resolves over time**: the order runs for `BOMBARDMENT_DURATION_DAYS` (14) and is ended by the operation's own `ExecuteOperation`, so the caller advances the clock and re-reads `bombarding` / `bombardmentTarget` / `endBombardmentReason` with `query.state` on the fleet. Each hit picks one weighted-random module from the hab's `OkayModules()` less the core module, so destroying a *named* module means polling `okayModules` and repeating the order, never asking for it; when `okayModules` reaches zero the next hit destroys the hab outright. The operation declares `MustAcceptCombat`, so a defended target can pull the fleet into combat, which cancels it |
| `nation.policies` | `nation`, `include_cancel?` | what national policies a nation can enact right now. A client can assert an option and a target without a screenshot. `nation` is a state id, a nation data name, or a display name (`Switzerland`). An ambiguous name is refused with the matches. Straight from `TINationState.AvailableSetPolicyOptionsWithTargets`, which returns one row per (option, target) pair. This is regrouped here into one row per option: `available: [{dataName, displayName, policyType, requiresTargets, requiresTargetConfirm, handledAtFactionLevel, targetCount, targets: [{id, type, name}]}]`, targets cut at 200 with `targetCount` carrying the true number. An option that takes no target contributes an empty target list. `unavailable` lists every other option the registry holds with `allowed` (its own `Allowed(nation)`) and `possibleTargets`. This is how a client learns *why* the option it wanted is missing. `executive` reports the faction holding the executive control point, its `benefitsDisabled` flag (set, the nation offers nothing at all), `powerConsolidated` and `daysUntilConsolidated`. `include_cancel` (default false) adds `CancelOption`, which the engine's list hides by default. This is echoed back as `includeCancel`. Refused for a nation with no control points at all. The engine reaches the executive one through a bare indexer. One asymmetry against `nation.set_policy`: an option that requires targets and has none contributes no pair. It lands in `unavailable` with `allowed: true`. `set_policy` would refuse it on target validation rather than on a gate. No vanilla option is in that state. Each one either counts its own targets inside `Allowed` or is paired with a single structural target (`DeclareIndependenceOption` answers `breakawayParent != null` and offers exactly that nation). |
| `nation.set_policy` | `nation`, `policy`, `target?` | enacts a national policy through `NationAI_AdoptPolicy`, the AI's own headless adoption. It is submitted the way the engine submits it (`GameControl.StartSimulationAction`, which is a bare `Execute()`, so it runs inside this frame). That action is exactly `if (policy.Allowed(nation)) policy.OnConfirm(nation, target)`. Nothing is bypassed and nothing is forced. Fixture-style force is `control_points` and the `spawn.*` verbs. `nation` and `target` each take a state id or a name (data name first, then display name). `policy` takes the option's data name, which is also its `PolicyType` member (`PeacefulBreakupOption`), or its display name (`Grant Independence`). **Gates, each a distinct refusal:** the nation has no executive control point. That control point has `benefitsDisabled`, which empties the policy list outright. The option is `HandledAtFactionLevel` (`ProposeAllianceOption`, `EndAllianceOption`, `InitiateRivalryOption`, `EndRivalryOption`, `EmployNuclearWeaponsOption` -- faction-level surfaces the engine keeps out of a nation's set-policy list, and out of this verb). `Allowed()` is false. The option is otherwise absent from `availableSetPolicyOptions`. Every one of those carries the conditions as read: executive faction, `benefitsDisabled`, `ExecutivePowerConsolidated`, `daysUntilExecutivePowerConsolidated`, `allowed`, `handledAtFactionLevel`, `requiresTargets`, `possibleTargets`. A `target` outside the option's `GetPossibleTargets` is refused with the list that is possible. An option whose `RequiresTargets` is true and no `target` is the same refusal. An option that requires none (`DisarmNuclearWeaponsOption`, whose single possible target is the nation itself) defaults to that one target and reports `targetDefaulted`. The adopt action's constructor reads `target.ID`, so an option with no target at all would run `OnConfirm(nation, null)` instead. This is what `enactedVia` reports. `CancelOption` is refused outright and is the one gate this verb adds. It drops the policy selection a landed `SetNationalPolicy` mission is waiting on and refunds that mission's cost to the executive faction. Since this verb never runs the mission, enacting it would be a refund for nothing -- clear a pending `PromptSelectPolicy` with the prompt verbs instead. Returns `{nation, executiveFaction, policy, target, targetDefaulted, cost, enactedVia, readback{notification, enactedNow, promptName, promptProbe, awaitingResponse, stillAllowed, targetStillPossible}}`. `cost` is always null. The nation-side path charges nothing, because the cost of national policy is the `SetNationalPolicy` councilor mission's. This verb does not run that mission -- no councilor is spent, no resource moves, and a `PromptSelectPolicy` prompt already queued by a mission that just landed is neither consumed nor cleared (only `ConfirmPolicyAction` removes it). Answer or drop it separately. **Policies do not all resolve inside the call.** The options deriving from `TIPolicyOptionWithConfirm` that this verb enacts (`JoinFederationOption`, `LeaveFederationOption`, `TransferRegionsOption`, `UnificationOption`, `EndWarOption`. The other two, `ProposeAllianceOption` and `EndRivalryOption`, are faction-level and refused above) pass at once only when the target's faction is the enacting nation's executive faction. Otherwise they queue a response prompt for the other side and pass, or not, whenever that side answers. This can be days later or never. Two of them override `PromptPolicyResponse` and do not follow that rule. `EndWarOption` queues unconditionally, at the war's enemy leader, so seeking peace never resolves inside the call. `LeaveFederationOption` tests `federation.hegemonicFederation` first, so leaving an ordinary federation always passes inside the call and only a hegemonic one applies the executive-faction test. Everything else, `PeacefulBreakupOption` (Grant Independence) included, passes inside the call. **`readback` captures the engine's record of the decision, never the downstream effect:** `notification` is the `LogPolicyAdopted` item this call pushed. It is found by walking the notification queue from its head down to a snapshot of that head taken before the call, with `enactedNow` true alongside it. The whole span is searched rather than the head alone because `DeclareIndependenceOption`, `TransferRegionsOption` and `EndWarOption` override `EnactPolicy` to log *before* `OnPassage`. Whatever their passage pushes (an independence notice, a region handover) sits on top of the policy record. `promptName` is the option's own `PromptName`, null for an option that cannot queue one. `awaitingResponse` is a prompt of that name in the queue whose `promptingGameState` is the enacting nation -- every `PromptPolicyResponse`, base and all three overrides, passes it. The pairing is what keeps another nation's proposal of the same type elsewhere on the map from answering for this one (an earlier proposal of the same type still outstanding from this same nation does read true). The two queue lists are private and are reached by reflection. A field that stops resolving makes `awaitingResponse` null rather than false and names itself in `promptProbe` (null otherwise). This also lands in the game log once at startup. `stillAllowed` and `targetStillPossible` re-read the gates afterwards, and an option that consumed itself reads false. `enactedNow` false with `awaitingResponse` false means the engine wrote no record of the decision at all. No vanilla option this verb enacts does that, so treat such a call as suspect rather than as a third mode. `LogPolicyAdopted` returns early on a negative `Importance`, which `CancelOption` alone carries and this verb refuses. It also returns early on a `JoinFederationOption` whose nation has no federation, where it logs an engine error and pushes nothing. `AddItem` also drops an item whose notification template is missing. What the policy then *does* -- releasing a nation, ending a war, moving regions -- happens inside `OnPassage`. Re-read the world with `query.state` or `nation.policies`, and advance the clock for anything waiting on a response. |
| `faction.diplomacy` | `nation`, `option?`, `target?`, `confirm?` | enacts the five `HandledAtFactionLevel` policy options, which are exactly the set `nation.set_policy` refuses by name, and this is the only contracted verb that reaches them. It is not the only reach: `action.invoke` can construct `ConfirmPolicyAction` with any registered option by data name, which enacts it with no cost, no eligibility check and no confirm at all. That is the raw bypass, deliberately available and documented as such; this verb is the gated path and the one to prefer. Membership is read off the live registry rather than hard-coded (`PolicyManager.policies` filtered by `HandledAtFactionLevel()`, which is `false` on the base and overridden to `true` by `ProposeAllianceOption`, `EndAllianceOption`, `InitiateRivalryOption`, `EndRivalryOption`, `EmployNuclearWeaponsOption` and nothing else), and any drift from that shape is named in `optionsAudit`, carried in every response and logged once. **With no `option` this is the discovery surface** and enacts nothing: `{nation, executiveFaction, cost, costPayable, holdings, nuclearWeapons, optionCount, optionsAudit, options[]}`, one row per option with `{dataName, displayName, policyType, relationChange, async, promptName, charged, requiresConfirm, requiresTargets, requiresTargetConfirm, handledAtFactionLevel, allowed, targetCount, targets[], costPayable, blockedBy}`, targets cut at 200 with `targetCount` carrying the true number and each nuclear target carrying its owning `nation`. `blockedBy` names the first gate an enact call would hit given a valid target, and null there means only `confirm` is left. **Enactment is `policy.OnConfirm(nation, target)` on the registry instance, on the main thread, inside this frame.** That is what the engine's own two call sites do: `NationInfoController.OnConfirmLaunch` calls `OnConfirm` directly, and `ConfirmPolicyAction.Execute` is a bare `OnConfirm` with no `Allowed()` re-check that returns immediately afterwards for a faction-level option. Nothing downstream enforces legality, so the gates below are the only guardrail, and they are `nation.set_policy`'s `RequirePolicyOffered` discipline applied against each option's own eligible list. **Gates in order, each a distinct refusal:** the `nation` does not resolve; the nation has no executive faction *and the option is one of the four relationship changes* (every path the engine takes to those four charges that faction and hands it on: `HandleFactionLevelRelationshipChanges` returns without acting when `executiveFaction` is null, `HandlePromptArmyOrderedToDepartDecision` pays from it before starting a `ProposeAllianceOption` confirm, and each `OnPassage` hands it to `InitiateAlliance` / `EndAlliance` / `InitiateRivalry` / `EndRivalry`; the nuclear option is deliberately *not* gated on it, because `AIDailyFactionPlanner.ConsiderNuclearAttack` calls `OnConfirm` directly in exactly that case, so refusing would be stricter than the engine); `option` is not one of the five, refused towards `nation.set_policy` when it names a real option that is handled nation-side; `target` is missing or outside the option's own `GetPossibleTargets`, which *is* the eligibility check (`eligibleAlliances`/`eligibleEndAlliances`/`eligibleRivals`/`eligibleEndRivalries` each run `CanAlly`/`CanEndAlliance`/`CanRival`/`CanEndRivalry` over the map, and `NuclearWeaponsTargets(false)` **reaches past enemy territory**: it takes every region of every nation at war, drops the ones out of reach unless the enactor has a space flight program (adjacency, plus water-adjacent regions when it has naval freedom), then *appends, unfiltered by reach*, every region of the enactor's **own** nation and of its **allies** that currently holds an enemy army -- the defensive-nuke branch -- and finally drops any enemy region carrying `antiSpaceDefenses`. So the list routinely contains your own regions and your allies', including your capital if an enemy army is standing in it, and firing on one is a legal call this verb will make. **Every target row carries its owning `nation`; check that field before firing.** The `antiSpaceDefenses` exclusion is interception, not distance, and applies only to the enemy-territory half) -- a named target that is a real nation but not an eligible one is resolved anyway so the refusal can carry the engine's own clause-by-clause `Can*Feedback` string with the TMP markup stripped; the option's own `Allowed(nation)` is false even though the target is eligible, which catches the one clause a target list does not carry -- `EmployNuclearWeaponsOption.Allowed` independently requires `numNuclearWeapons > 0` and `NuclearWeaponsTargets` has no stockpile term, so a nation at war with an empty stockpile still lists targets and would otherwise fire, decrementing a count `ChangeNumNuclearWeapons` clamps at zero while the strike still lands as permanent campaign state (checked generically, so a future option with clauses beyond target count is covered); the executive faction cannot pay; `confirm` is absent. **Cost.** The four relationship options pay `TINationState.FactionLevelRelationShipChangeCost` (which is `TIFactionState.setPolicyMission.cost`) from the executive faction, with the engine's own `"Relationship Change"` label, *before* `OnConfirm` -- the same call in the same order as `HandleFactionLevelRelationshipChanges`, because legality-preserving means cost-preserving. `PayCost` makes no affordability check of its own, so the `CanAfford` gate above is it, and a refusal names the cost and what the faction holds. The nuclear option charges nothing: its UI path pays nothing either. Which options are charged is keyed on `relationChange != None`, the same value the engine's dispatcher switches on, so the rule cannot drift from what it mirrors; every faction-level option that is *not* one of the four requires `confirm:true`, so a sixth option added by a game update lands on the cautious side. **Two of the five do not resolve inside the call.** `ProposeAllianceOption` and `EndRivalryOption` derive from `TIPolicyOptionWithConfirm` and take the base `PromptPolicyResponse`: they enact inline only when `target.ref_faction == nation.executiveFaction` (one faction holding the executive control point of both nations), and otherwise queue `PromptRespondToFormAllianceCall` / `PromptRespondToEndRivalryCall` at the target with the *enacting nation* as `promptingGameState`, and pass, or not, whenever that side answers -- days later or never. `readback.awaitingResponse` is **target-scoped**, unlike `nation.set_policy`'s, which is nation-scoped: it matches a prompt of that name whose `promptingGameState` is this nation *and* whose `actingState` is this target. Both async options here take the base `PromptPolicyResponse`, which passes `policyTarget` as `actingState`, so that triple identifies one proposal and the USA proposing to Canada and then to Mexico no longer reads the second call as already-pending. (`nation.set_policy` cannot narrow this way: its options raise prompts at three different acting states.) ## Mod inspection

Templates and both mod loaders finish at boot. The mod verbs answer with no
campaign loaded.

DLL mods come from `UnityModManager.modEntries`. Template mods come from the game's own
records. These are read and never rebuilt. `ModManager.ModNames` / `DisabledModNames`
are for the folders the loader accepted. `ModTemplateManager.jsonMods` is for the
individual JSON files it merged. Each carries its load order, its target vanilla file,
the data names it touches, and whether it matched a vanilla template at all. A file
that matched nothing is the shape that crashes template load.
`TIPlayerProfileManager.useMods` is the `use mods` checkbox. With it off, JSON and
localization mods are ignored outright. The folder listing from `Mods/Enabled` and
`Mods/Disabled` is reported alongside for cross-checking what the loader saw against
what is on disk.

`query.template` reaches templates through `TemplateManager.GetAllTemplates<T>`. This
is bound at runtime to the class named by `type`. The name is resolved against
Assembly-CSharp with and without the `TI` prefix and the `Template` suffix. It
falls back to a by-name sweep of every loaded assembly so a class added by a DLL mod
resolves too. Results are cached, misses included. Lookup keys off the exact class.
This is the 1:1 match for one template JSON file. A class whose entries all belong to
subclasses is retried with subclasses included.

One entry is serialized by Newtonsoft over the live object. Members pointing at other
templates collapse to a data name. Game states collapse to `{id, type, name}`. Unity
assets collapse to an asset name. `System.Type` collapses to a type name. This stops
one entry from dragging in the rest of the template graph. Reference loops are dropped.
Enums are written by name. A member whose getter throws is listed in the response's
`errors` instead of failing it. An entry that serializes past the response budget is
refused.

`query.enums` answers the question "what are the legal values of this template field".
A client cannot work this out from `query.template` alone. The serializer writes enums
by name. An entry never reveals the member set it was chosen from. It never reveals
whether a number a mod wrote is the same value under a different spelling. The verb
reads the member names and ordinals straight off the type with `GetRawConstantValue`.
It derives the field-to-enum map from `FieldInfo.FieldType`. It walks base classes so
the answer is one lookup rather than a chain. It reads fields only, never properties. A
`ReflectionTypeLoadException` from another DLL mod is caught. The unloadable types are
counted into `errors` rather than failing the verb. A partial table is always
distinguishable from a complete one.

The whole table is one response by design. It is roughly 69 KB against a 512 KB budget.
Splitting it would let a client pair an `enums` map from one game process with a
`classes` map from another. The serialized string is cached per scope for the process
lifetime. The loaded assembly cannot change inside one.

Harmony is reached by reflection. The bridge patches nothing. It loads with no Harmony
present. In that case, the verb answers an empty list.


## Combat

Combat blocks the strategy clock. While any unresolved `TISpaceCombatState`
exists, or the precombat canvas is up, or an active-player prompt is queued,
the simulation tick stops advancing time. Every combat has to be disposed of
before a run can continue.

A combat between two AI factions disposes of itself. The precombat listeners
answer their own stance prompts. The precombat interaction ends without the
screen ever being shown. The simulation callback writes the result back.
`combat.autoresolve` reports such a combat as resolving automatically and does
nothing.

A combat the active player is in stops and waits for the player. Resolving it
headlessly means taking the same route the precombat screen's own buttons take.
It takes one step per frame:

1. Wait for the combat to be promoted and picked up by the precombat controller.
2. Submit the player's stance through `PrecombatController.StanceSubmit`.
   Prefer Defend among the stances the combat allows. This runs the same
   player action the button runs and is synchronous.
3. Wait until both stances (and both bids, when the stance pair demands bidding)
   are in. Only AI factions may be outstanding here. The game's prompt handler
   serves AI factions only. The wait loop that runs after the precombat
   interaction ends would never see a human answer. An outstanding non-AI
   faction fails the verb rather than risking that loop.
4. `PrecombatController.AutoresolveSelected()` to end the precombat interaction.
   This starts the simulation coroutine.
5. Poll `autoresolving`. When it clears,
   `PrecombatController.OnAcceptAutoresolveSelected()` applies the result.
   It clears the blocking prompt, and ends the combat.
6. Applying the result raises the combat-ended event. This puts the post-combat
   report on the precombat canvas. The simulation tick returns early while that
   canvas is enabled. Leaving it up stops every later combat from being
   promoted and stops the clock. `PrecombatController.OnClosePostCombatButtonSelected()`
   closes it. This is the same call the human's close button makes. It also replays a
   combat that arrived while the report was up, which the controller defers.
   Time is not touched. The vanilla continue button pairs that close with
   `gameTime.Play()`. The bridge deliberately calls only the close. It leaves
   speed and pause to the client.

The work runs in the per-frame tick, never inside the verb. No step can hold
a frame. A step that throws disarms and leaves the reason in
`combat.status.autoresolve.error`. A resolution that stops making progress
disarms on a frame budget rather than staying armed.

A client that wants a fight flown by a human simply does not call
`combat.autoresolve`. The combat stays pending. `combat.status` reports it and
the block. The client resumes once a person has taken it.

## Campaign entry

`campaign.new` drives the start screen rather than assembling a scenario itself. The
menu controller already holds a live scenario built at scene start. It holds a faction
list, a difficulty dropdown, and a start button that reads all three. The verb sets
those controls and presses the button.

Order is fixed. It sets scenario, then the other options, then difficulty, then
faction. Choosing a scenario rebuilds the allowed-faction list and resets the faction
dropdown. A faction set before it would be discarded. A `FactionCouncils` option
rebuilds that list too. This is why every option is written before the faction is
picked. Difficulty is an index into the four start-screen levels. It is reported as the
campaign's own 1-4 numbering. The campaign reads the dropdown directly at launch. The
default-options pass the start button runs restores everything else from the last
recorded difficulty rather than from the control. The tutorial toggle is forced off
through its own handler. It defaults on for a player's first ever game. The tutorial
gates the map behind scripted steps no client can answer.

An `options` entry is a meta template dataName. The template carries the category it
belongs to. The wire format is names alone. The verb writes each one where the
picker's dropdown would have. An empty entry, a name matching no meta template, a
template that is not a new-campaign option, a category the scenario arg owns, and two
options in one category are each refused. The whole list is resolved before the
first option is written. A rejected list leaves the option map untouched. The
scenario arg is settled ahead of all of this. It stands whatever happens to the
options. `query.scenarios` lists every selectable option grouped by category.

Three of the menu's private members are read by reflection. The allowed-faction list
its dropdown handler indexes is what a faction name is matched against. The start
options map is reported back as the categories the launch will read. The scene
manager's absence means the menu never finished its own start. The controls the verb
sets and the methods it calls are public.

Launching reloads the scene. The verb returns the choices it made and leaves the
wait to the client, as `saves.load` does. It refuses while a campaign is loaded, when
the menu has not finished its own initialization, and while either the start screen's
or the load menu's loading screen is up. That last check is what stops a second launch.
A scene load takes tens of seconds and produces no campaign until it finishes. Every
other guard still passes. The loading screen each route raises is the only standing
record that one is already running.

## Prompts

A prompt in either of the active player's queues stops the simulation tick and pauses
time. Prompts belonging to other factions never block. The game's own prompt handler
answers them. It answers them only for AI factions. This is why the player's
queue accumulates instead.

`prompts.dismiss` takes two passes.

The screens pass repeats what the vanilla Autopilot does in a frame. This is the map of
every modal that can strand an unattended campaign. It handles the alert box (okay,
then close, then go-to, repeated while any is live, then the first live option button
on a notification that carries a choice). It handles the policy panel cancelled and
confirmed, the diplomatic response panel declined, an ally's war call declined, and a
faction greeting continued. It handles the diplomacy screen closed, an illegally-placed
army sent home, the research screen closed, and a trajectory change cancelled. Each is
guarded on its own so one failure does not stop the rest. The precombat screen is
deliberately absent. `combat.autoresolve` owns it and drives it a step per frame.

The prompt pass answers by name. It runs the player action the game's own AI path would
run. This includes a tech and a project chosen by the AI's selection strategies. It
includes councilor missions confirmed through the assignment screen's button. It
includes an unassigned org sold when the faction is over its org limit. Anything else
is reported as skipped with the reason.

`all` then drops whatever is still queued. The decision behind such a prompt goes
unmade. This costs a research slot or a mission phase and leaves the save intact.
It is the difference between a run that continues and a run that sits paused forever.

## Serialization rules

- Query verbs return curated, hand-built flat objects. Raw game objects are
  never fed to a general-purpose serializer. The state graph is cyclic and
  huge.
- Game-state references collapse to `{id, type, name}` everywhere. This includes
  inside `query.state`. The client walks the graph by issuing more queries.
- Newtonsoft (ships with the game) does the JSON encoding.

## Compatibility

Response fields may grow. Clients must tolerate unknown fields. All list responses
carry paging fields (`count`, `returned`, `truncated`) alongside the items.
