# TerraInvictaMCP wire protocol (in-game DLL)

This DLL mod is loaded by Unity Mod Manager (UMM). It uses Harmony to patch
game methods at runtime. It runs a localhost TCP server -- the
bridge -- inside Terra Invicta. External tools like AI agents or scripts
speak the protocol -- Claude Code, OpenCode, Antigravity, or plain netcat.
They can drive a running campaign, issue commands, read game state as JSON,
and control time without the GUI. A verb is one named request the bridge answers.

This document describes the contract shipped with mod version 0.1.0. Verbs
added after that carry a "since <version>" note on their row.

## Design principles

- **Thin DLL.** The mod exposes simple verbs. Sequencing, judgment, and test
  logic live in the client scripts. A DLL change requires a game restart. A script
  change costs nothing.
- **Never crash the game.** Every command runs inside a catch-all block. Failures
  return an error response. A broken bridge degrades to an inert mod. One verb sets
  the principle aside because crashing the game is its whole purpose:
  `test.crash_the_game` is a test fixture for the crash flag below. It runs inside the
  same catch-all as every other verb and never throws -- it puts the game into its crash
  state and answers normally over it -- and it refuses to run without an explicit
  confirmation argument.
- **Grow on demand.** New verbs are added only when a task cannot be done
  with existing ones. Unknown commands return an error. Clients can
  feature-detect against `version`.

## Transport and protocol

- TCP on `127.0.0.1:17470`. Localhost only, no auth. Anything on this machine
  already has the same user privileges. If the bind fails, log one line and
  run inert.
- Newline-delimited JSON (NDJSON: one JSON object per line), UTF-8. Request: `{"id": <int>, "cmd": "<verb>",
  "args": {...}}`. Response: `{"id": <int>, "ok": true, "data": ...}` or
  `{"id": <int>, "ok": false, "error": "<message>"}`.
- **Since 0.1.1 every response envelope also carries `clockStall`**, beside
  `ok` on the success and the error frame both: seconds the game has gone
  without gaining time, or null when there is nothing to measure (no campaign,
  or no frame yet since one loaded). A per-frame watchdog measures it against
  `Time.realtimeSinceStartup`, so a stopped game clock does not stop the
  measurement, and the timer restarts when a campaign loads, so a save reloaded
  to the date it was saved at does not inherit the stall of the campaign it
  replaced. Two conditions count as a stall: the clock not moving, and the
  clock crawling -- speed index below 3 with no `run_until` armed, where the
  date changes every frame while an hour of real time buys a day of game time.
  It is on the envelope rather than on a verb because a client learns the stall
  from the calls it was making anyway, including the ones that failed, which is
  where it would otherwise learn nothing. Past each whole five minutes the DLL
  also writes one line through the UMM logger (Player.log, `log_tail
  which=player`): `[TerraInvictaMCP] clock stalled N s, state=<state>,
  prompt=<blocking prompt or none>, last verb <M> s ago`. That line is written
  only after some client has executed at least one verb in this session: a
  person playing with the mod installed pauses for five minutes as a matter of
  course, and the stall is a harness failure rather than theirs. A client
  written before the `clockStall` key ignores it.
- Multiple concurrent connections are accepted. All commands funnel into one
  FIFO queue. Each connection gets responses in the order it sent requests.
- A wire-contract change is a mod version bump. This is reported by `version` as
  `mod`. This document notes the version a verb appeared in.

## Execution model

- A background thread owns the socket to accept, read lines, and enqueue.
- Commands run on the main thread from the UMM `OnUpdate` callback. This
  survives scene reloads and save loads. The queue drains once per frame.
- Verbs must complete within a frame. Anything long-running is started by one
  verb, advanced by a per-frame tick, and observed by polling (see
  `time.run_until` and `combat.autoresolve`).
- With no campaign loaded, game verbs return `error: "no campaign"`. The verbs `ping`
  and `version` always work.
- The bridge outlives a crash in game code, so a client must read the crash flag
  rather than infer a dead game from a frozen clock. `GlobalInstaller.HandleException`
  sets `GameControl.handlingException`, shows the crash panel, calls `PauseAndBlock`,
  clears every event listener and turns input off; the mod's update runs off the mod
  loader's own MonoBehaviour, so every verb keeps answering over all of it and the
  blocked clock reads exactly like a modal alert. `query.time.crashed` and
  `version.crashed` report the flag. Recovery is a process restart: the flag has one
  writer in the assembly, no clearer, and survives a scene load, so a save loaded into
  the same process comes back with Escape dead and two combat controllers returning
  immediately from their per-frame methods. `test.crash_the_game` puts the game into
  exactly that state on demand, so a client's handling of it can be tested rather
  than waited for.
- **The clock must not be handed back into an open councilor mission phase.**
  `TIMissionPhaseState.StartNewMissionPhase` opens by testing its own
  `phaseActive`: a semimonthly tick that lands while the previous phase is
  still running logs `StartNewMissionPhase fired when mission phase was
  already active`, clears `phaseActive` and returns with
  `factionsSignallingComplete` still populated, so the next phase ends early
  on the stale list and the damage sustains itself. What walks into it is game
  time reaching the next semimonthly tick while the phase is open, so what a
  driver must withhold is the clock itself, not merely the `run_until` target:
  a client that sets speed 5 and plays with the target unarmed collides just
  the same. So `query.time` reports the phase, and a driver holding a phase
  issues no `time.speed` and no `time.play`, pauses a clock that is running,
  and hands all three back only once the phase reads closed. `time.run_until`
  refuses a new target while one is open as well, since arming also clears the
  driver's park; `force: true` overrides it. The phase closes when every
  faction has signalled its
  assignments, which for the player means the mission-assignment confirmation
  `prompts.dismiss` presses -- a wait that watched only the clock would never
  end. Under an `ai.control` engagement the colliding tick is deferred instead
  (see `ai.control`), and the two counters never move together:
  `deferredPhaseTicks` counts collisions prevented while engaged,
  `missionPhase.collisions` counts collisions taken while not.

| `query.factions` | | per faction: id, name, alien flag, active-player flag, resources, hate/mood summary |
| `query.habs` | `faction?` | per hab: id, name, tier, type, owner, body/site, module count |
| `query.fleets` | `faction?` | per fleet: id, name, owner, location, ship count, in-combat flag |
| `query.state` | `id` XOR `root`, `path?`, `include_private?` | reflection dump at depth 1 of whatever the arguments land on. Start from `id` (a registered game state) or `root` (a static entry point). Exactly one is required. `path` then walks from there. **Grammar:** identifier segments separated by dots. Each segment can optionally carry one `[n]` integer indexer applied to an `IList` or array -- `player.aiValues`, `currentSpeeds[2].displayName`. Dictionary keys are not addressable. Fields are tried before properties. A property getter runs game code. **A getter that mutates is the caller's risk**. The member dump invokes public getters too. A member re-declared with a narrower type in a subclass, as `template` is on `TIHabState`, `TISpaceBodyState`, `TILagrangePointState` and `TISpaceFleetState`, resolves to its most derived declaration. It does not fail on the ambiguity. Each step is guarded. A step that fails is an error naming the segment and the type it failed on (`no member 'aiValues' on TIPlayerState at segment 2`, or `at root segment 2` for a segment inside `root`, whose static member is segment 1 and whose trailing members continue from there). It does not return a silent null. A null answer and a wrong member name are otherwise indistinguishable. **`root`** is `TypeName.Member[.Member...]`. The type resolves against Assembly-CSharp first. A bare name is retried in `PavonisInteractive.TerraInvicta`. It then checks every loaded assembly, then does a by-name sweep. Results are cached, including misses. A namespace-qualified type name carries dots of its own. The longest prefix that resolves to a type wins. The rest are members. The first member is static. `root` without `path` is fine. **`include_private`** (default false) adds non-public instance members to both member lookup and the endpoint dump. It walks the base chain by hand because reflection does not inherit them. A private member whose name a public one already took is skipped. **Endpoint:** a game state answers `{id, type, name, members}` as before. A value the dump renders whole (string, enum, number, bool, date, template as its `dataName`, or an expandable list) answers `{type, value}`. **Since 0.1.1 a `Dictionary<K,V>` the walk lands on answers `{type, value}` too**, when both its type arguments pass the member-dump list test, with each side rendered the way a list item is: a JSON object keyed by the rendered key, a template key as its `dataName`, an enum key by name, a game-state key as `name (id)`. Two keys that render to the same text (two templates sharing a `dataName`) would collide in a JSON object and lose an entry silently, so that case answers an array of `{key, value}` pairs instead, every pair whose key repeats carrying `duplicateKey: true`. The test is on the runtime type, so a member declared `IDictionary<K,V>` expands when what it holds is a `Dictionary<K,V>`. This is how `TIFactionState.objectives` and `objectiveNames` (both private: `path=objectives include_private=true`) and `TIControlPoint.controlPointPriorities` are read. **It applies at the endpoint only** -- walk onto the dictionary with `path`; in a member dump it stays a bare type name. That is deliberate: `TIFactionState` alone declares 46 dictionaries, 36 with both type arguments expandable (12 public, 24 more under `include_private`), and one of them, `cachedTechTooltipStrings`, holds prebuilt tooltip text whose first 200 values approach the whole 160000-character response budget. `intel` and `highestIntel` are keyed by `TIGameState`, so expanding them in a dump costs up to 400 `GetDisplayName` calls on the main thread for a question nobody asked. Anything else answers `{type, members}`. Every response echoes `root` and `path`. **Members:** scalars verbatim, game-state refs collapsed to `{id, type, name}`. A list or single-dimension array expands when its declared element type is a game state, a template (each its `dataName`), a string, an enum (by name), or a number or bool. A dictionary stays a bare type name here, as a nested list does. This keeps one member from dragging in the rest of the graph. **Caps:** 16 dot-separated parts in `path` and in `root` alike. Both are refused on the split before anything is parsed or resolved. A root prefix that misses costs a sweep of every loaded assembly. The queue drains on the main thread. An expanded list or dictionary cuts at 200 entries, and an expanded dictionary also cuts at 65536 characters, since the entry cap bounds the number of pairs and says nothing about the size of one. Each pair is measured before it is kept, so the budget bounds the response rather than the response minus its last entry; the first pair is always rendered whatever its size. **At the endpoint the cut is reported**: the response carries `valueCount` (the collection's own count, null when it does not report one), `valueShown`, `valueTruncated` and `valueTruncatedBy` (`entries`, `characters`, or null), so "key K is absent" past the cap is not a silent false negative. A dictionary also carries `valueShape` (`object` or `pairs`): the collision test can only see the entries the walk reached and dictionary enumeration order shifts as the engine mutates one, so the same path can answer an object on one call and pairs on the next, and the field says which without the client inferring it from the JSON type. Inside a member dump a list still cuts with no marker, as it always has. |

It is echoed as `narrativeMode` on the reply; an unknown value is echoed as given, since the behaviour is carried by `narrative`. **Since 0.1.1 an event with one option is pressed under every setting**, `narrative: false` included: `numOptions == 1` (clamped to `eventOptions`) is a box with nothing to weigh, and leaving it standing blocks the clock on a button whoever was left the choice would press anyway. Non-narrative screens are still cleared. Returns the screens closed, the prompts answered and how, the prompts skipped and why, what remains, and `narrativeNotes`. What the prompt pass produces travels in `dismissed` instead, an ordinary answer and the drop described below alike, and neither is written to `screens`, since neither closes one. | `alert.choose` | `option?`, `detail?` | the open alert box: whether one is up, its text, and its live option buttons with labels. With `option`, presses that button. An option button on this controller always belongs to a narrative event -- every path through `NotificationScreenController.OnOptionButtonPressed` past its guard builds a `SelectNarrativeEventOption` with the index pressed -- so pressing one IS answering the event. `prompts.dismiss` presses the option its narrative strategy picks, or none at all under `narrative: false`, which is what leaves the box up for this verb. A press is also refused when the controller is not yet taking narrative input, since the engine would discard it without a trace; **`pressLands`** reports that state up front, because a live option button is not yet a press that lands and a client polling the box should wait a poll rather than earn the refusal. **`detail`** adds, per live option, what that option would do: `text` (`optionButtonDetail`, the popup's own words), `valid` (`NarrativeEventOption.ValidOption`), `baseAIPreference`, the two conditions as text, and `outcomes` -- each with its `chance` from `outcomeChance`, `weight`, `aiFavored`, `effects`, `delayedEffects`, `addsEvents`, `removesEvents`, `projectGranted`, `orgGranted` and `costs`. ## Ship designs

`design.create`, `design.delete` and `design.auto` cover a surface nothing else
in the bridge reaches. A ship design is a `TISpaceShipTemplate` built at run
time and registered with `TemplateManager`, and the only way a player makes one
is the ship designer: a hull picker, a drive picker and a slot grid, all mouse.
For a driving agent the UI is view-only, so before these verbs the designs a
test could use were the designs the campaign happened to ship with, and the
question "does this mod's laser fit on a vanilla hull" had no headless answer.

`design.create` is the by-hand path and takes every part by name. It is not a
fixture in the `spawn.*` sense: it enforces the engine's own validity, and with
`legal` it enforces the engine's own research gate too, so a refusal is a real
answer about the parts rather than a limit of the harness. `legal: false` is the
fixture, and it says so.

`design.auto` is the engine's own search, and `spawn.fleet` is the other half of
both: a design proves the parts go together and are buildable, `spawn.fleet`
proves it flies.

## Mod inspection

Templates and both mod loaders finish at boot. The mod verbs answer with no
campaign loaded.

DLL mods come from `UnityModManager.modEntries`. Template mods come from the game's own
records. These are read and never rebuilt. `ModManager.ModNames` / `DisabledModNames`
are for the folders the loader accepted. `ModTemplateManager.jsonMods` is for the
individual JSON files it merged. Each carries its load order, its target vanilla file,
the data names it touches, and whether it matched a vanilla template at all. A file
that matched nothing is the shape that crashes template load.
`TIPlayerProfileManager.useMods` is the `use mods` checkbox. With it off, JSON and
localization mods are ignored outright. The folder listing from `Mods/Enabled` and
`Mods/Disabled` is reported alongside for cross-checking what the loader saw against
what is on disk.

`query.template` reaches templates through `TemplateManager.GetAllTemplates<T>`. This
is bound at runtime to the class named by `type`. The name is resolved against
Assembly-CSharp with and without the `TI` prefix and the `Template` suffix. It
falls back to a by-name sweep of every loaded assembly so a class added by a DLL mod
resolves too. Results are cached, misses included. Lookup keys off the exact class.
This is the 1:1 match for one template JSON file. A class whose entries all belong to
subclasses is retried with subclasses included.

One entry is serialized by Newtonsoft over the live object. Members pointing at other
templates collapse to a data name. Game states collapse to `{id, type, name}`. Unity
assets collapse to an asset name. `System.Type` collapses to a type name. This stops
one entry from dragging in the rest of the template graph. Reference loops are dropped.
Enums are written by name. A member whose getter throws is listed in the response's
`errors` instead of failing it. An entry that serializes past the response budget is
refused.

`query.enums` answers the question "what are the legal values of this template field".
A client cannot work this out from `query.template` alone. The serializer writes enums
by name. An entry never reveals the member set it was chosen from. It never reveals
whether a number a mod wrote is the same value under a different spelling. The verb
reads the member names and ordinals straight off the type with `GetRawConstantValue`.
It derives the field-to-enum map from `FieldInfo.FieldType`. It walks base classes so
the answer is one lookup rather than a chain. It reads fields only, never properties. A
`ReflectionTypeLoadException` from another DLL mod is caught. The unloadable types are
counted into `errors` rather than failing the verb. A partial table is always
distinguishable from a complete one.

The whole table is one response by design. It is roughly 69 KB against a 512 KB budget.
Splitting it would let a client pair an `enums` map from one game process with a
`classes` map from another. The serialized string is cached per scope for the process
lifetime. The loaded assembly cannot change inside one.

Harmony is reached by reflection. The bridge patches nothing. It loads with no Harmony
present. In that case, the verb answers an empty list.


## UI

Three verbs cover the screen, and they are meant to be used together.
`ui.screenshot` captures whatever is on it, `ui.view` chooses between the solar
system and the political map, and `ui.screen` opens an info screen, the space
object detail panel or a rename panel. The bridge never sends synthetic input,
so a panel with no verb behind it cannot be captured and therefore cannot be
tested: that gap, not renaming or navigation, is why the two drives exist.

Both drives change UI state and neither changes game state. Both need a
campaign, because `CanvasManager` builds its screen registry when the campaign
UI loads and holds nothing at the start screen. Both close over the engine's own
entry points -- `ViewControl.GotoView`, `CanvasManager.ShowInfoScreen<T>`,
`HabDetailRequested`, `SpaceObjectDetailController.ViewSpaceObject` -- rather
than reaching into controllers, and each refuses the arms another verb owns:
`ui.view` will not unload the campaign (`game.main_menu`) and will not enter or
leave the combat view (the combat verbs).

**Read the reply rather than assuming the screen moved.** One of these paths is
synchronous and one is not. `ShowInfoScreen<T>` and `ViewSpaceObject` are direct
calls and have landed when the verb returns. `HabDetailRequested` is a queueable
event, so `EventManager` drains it from its own `Update` on a later frame and
`ui.screen hab=<id>` answers `deferred: true` with the screen as it stands now.
Capture after a second call has confirmed it, not after the first.

The reverse holds for `detail`: the panel arrives inside the call, and the info
screen it displaces leaves a frame later, because `SetActiveInfoPanel` raises
`InfoPanelOpened` and `CanvasManager`'s listener for it is queueable. The reply
carries `infoScreenCloseQueued` and names the screen still standing. A `rename`
in that same frame goes to the detail panel for the same reason.


## Combat

Combat blocks the strategy clock. While any unresolved `TISpaceCombatState`
exists, or the precombat canvas is up, or an active-player prompt is queued,
the simulation tick stops advancing time. Every combat has to be disposed of
before a run can continue.

A combat between two AI factions disposes of itself. The precombat listeners
answer their own stance prompts. The precombat interaction ends without the
screen ever being shown. The simulation callback writes the result back.
`combat.autoresolve` reports such a combat as resolving automatically and does
nothing.

A combat the active player is in stops and waits for the player. Resolving it
headlessly means taking the same route the precombat screen's own buttons take.
It takes one step per frame:

1. Wait for the combat to be promoted and picked up by the precombat controller.
2. Submit the player's stance through `PrecombatController.StanceSubmit`.
   Prefer Defend among the stances the combat allows. This runs the same
   player action the button runs and is synchronous.
3. Wait until both stances (and both bids, when the stance pair demands bidding)
   are in. Only AI factions may be outstanding here. The game's prompt handler
   serves AI factions only. The wait loop that runs after the precombat
   interaction ends would never see a human answer. An outstanding non-AI
   faction fails the verb rather than risking that loop.
4. `PrecombatController.AutoresolveSelected()` to end the precombat interaction.
   This starts the simulation coroutine.
5. Poll `autoresolving`. When it clears,
   `PrecombatController.OnAcceptAutoresolveSelected()` applies the result.
   It clears the blocking prompt, and ends the combat.
6. Applying the result raises the combat-ended event. This puts the post-combat
   report on the precombat canvas. The simulation tick returns early while that
   canvas is enabled. Leaving it up stops every later combat from being
   promoted and stops the clock. `PrecombatController.OnClosePostCombatButtonSelected()`
   closes it. This is the same call the human's close button makes. It also replays a
   combat that arrived while the report was up, which the controller defers.
   Time is not touched. The vanilla continue button pairs that close with
   `gameTime.Play()`. The bridge deliberately calls only the close. It leaves
   speed and pause to the client.

The work runs in the per-frame tick, never inside the verb. No step can hold
a frame. A step that throws disarms and leaves the reason in
`combat.status.autoresolve.error`. A resolution that stops making progress
disarms on a frame budget rather than staying armed.

### A combat that ends with nothing to accept

Steps 5 and 6 assume a simulation the player accepts. Not every combat produces
one, and two different engine paths take the combat away instead. The machine
is sitting in an earlier phase when either happens, waiting for something that
will not arrive, until the combat disappears from under it.

**The combat was never promoted.** This is the common one, and the one a
fixture-built fight hits. `combat.start` only caches its two fleets and its
hab; `TISpaceCombatState.StartCombatFromStrategyLayer` promotes the combat a
frame or more later, and when the cached assets fail its gate it archives the
combat, removes it from the `GameStateManager` and calls
`SpaceCombatManager.SetCombat(null)` instead. `InitializeCombat` never runs and
`Autoresolve` is never reached. The gate's clauses are on the `combat.status`
row above; `promotionAtArming` is that gate snapshotted when the machine armed,
which is the only surviving evidence once the combat is gone.

**`Autoresolve` ended it outright.** `TISpaceCombatState.Autoresolve` simulates
when `fleets[1]` **or** `hab` is non-null; otherwise it calls its own local
`EndCombat`, which is `RecordSurvivors`, `EndCombatForStrategyGame` and
`SpaceCombatManager.SetCombat(null)` and nothing else. No `SimulatedCombat` is
ever set, `autoresolving` is never raised, and the combat is archived and gone.
Reaching that branch needs both fields null at once, and `InitializeCombat` is
the only writer of `fleets[1]`, so past a successful promotion it means a
hab-only combat whose `hab` `HandlePrecombat` nulled -- a defender that evaded.
A two-fleet fight cannot get there.

`PromptBeginCombat` is the casualty. `PrecombatController.OnCombatInitiated`
queues it, and **every** engine path that removes it is one of that screen's
own button handlers -- `OnAcceptAutoresolveSelected`, `CloseResolveSelected`,
`LiveResolveSelected`, `CancelAttackButton`, `OnRejectAutoresolveSelected`.
None of them runs on this path, and an unhandled faction prompt is ignored in
silence rather than dropped, so one left standing blocks saving and holds the
clock for the rest of the campaign.

So the tick, on finding its combat gone with no canvas left to close, removes
that prompt itself before disarming, with the engine's own five-field removal,
and says so in `combat.status.autoresolve.note`. The note survives the disarm;
it is cleared by the next arm.

### Arming again after a failure

A failed tick disarms, so a client polling for a combat sees one present and
nothing armed and calls `combat.autoresolve` again. Arming re-enters the
machine at the start, which defeats the guards steps 4 and 5 rest on: those
advance the phase before making a call that must not repeat, and an arm resets
the phase. A second `AutoresolveSelected` raises a second `PrecombatComplete`.
A second `OnAcceptAutoresolveSelected` reaches `ApplySimulatedCombat`, which
writes the same battle's damage into the real game states.

So the machine keeps a record of what the last failure on a combat left behind,
and that record outlives the disarm. `combat.status.autoresolve` carries it:
`attemptedCombat`, `attempts`, `reached` (the furthest phase entered),
`errorKind`, `firedAutoresolveSelected`, `firedAcceptAutoresolve`, and
`retryable`, which is the arming decision itself. Arming is refused, with the
combat, the phase and the error named, when either one-shot has fired, when the
failure is one no retry changes (a stance or bid owed by a second seated
faction, a controller whose active player is stale, a controller that lost the
combat), when the stall was in the closing phase (the combat is archived and
the canvas is still up, so no arm reaches it), or after two attempts. A
transient failure -- no controller yet, no active player yet -- is worth the
one retry the budget allows. The record is cleared when a different combat is
armed.

**The double-apply guard has no reachable trigger, and looking for one costs
more than it settles.** Two live runs resolved their combat on the first arm,
`attempts: 1`, damage applied once, which is the normal path and the only one
the harness produces. The way to induce a stale controller from outside was a
console `setfaction` to another faction with the precombat screen up, and that
is retired: it orphans the armed combat (the canvas is dropped and the combat
id stops resolving), and it moves the seat to an AI faction, which is unsafe
while the AI's mission planner is live -- the planner assigns a mission through
the human UI's map controller and the game dies in `MapController.Fly` on a
visualizer only the human faction's councilors carry. So the guard stands as
written, unexercised, and the state it guards against stays hypothetical.
`prompts.dismiss` refuses to run at all once the seat has moved off the
faction the campaign came up with (see its row).

`combat.precombat` is where to look after a refusal, starting with
`action=status`, which reports whether the canvas is up and which buttons are
live. It is not guaranteed to be a way out: `AutoresolveSelected` ends the
precombat interaction, and `EndPrecombatInteraction` deactivates
`preCombatUIObject` and hides the canvas, so a dead end reached after step 4
may have no button left to press. Dropping `PromptBeginCombat` is never the
answer either -- it is the canvas and not the prompt that freezes the clock.
The dead ends reached BEFORE step 4 do have a live cancel button.

With `ai.control` engaged, `combat.autoresolve` refuses rather than reporting
the combat as resolving automatically. The engagement's postfix makes the
engaged faction report `isActivePlayer` false, which is what keeps the AI's
strategic reads honest, but `PrecombatController` takes its faction from
`CanvasControllerBase.activePlayer`, which is copied from `GameControl` and is
untouched. The canvas comes up and holds the clock either way, so the
"resolving automatically" answer would be false and a client would re-ask
forever.

A client that wants a fight flown by a human simply does not call
`combat.autoresolve`. The combat stays pending. `combat.status` reports it and
the block. The client resumes once a person has taken it.

The precombat screen still asks that client for two things, and they have
separate answers. The stance is `combat.stance`, which submits through the same
button step 2 above takes and reports the stance read back off the combat;
`prompts.dismiss` answers the same prompt with Defend on its own whenever the
screen is up and nothing is autoresolving, so `combat.stance` is for picking a
different one. `PromptBeginCombat` is answered by nothing: every button that
clears it commits an outcome, so `combat.precombat` presses the one the client
means and the prompt is never dropped instead -- it is the canvas that freezes
the clock.

## Campaign entry

`campaign.new` drives the start screen rather than assembling a scenario itself. The
menu controller already holds a live scenario built at scene start. It holds a faction
list, a difficulty dropdown, and a start button that reads all three. The verb sets
those controls and presses the button.

Order is fixed. It sets scenario, then the other options, then difficulty, then
faction. Choosing a scenario rebuilds the allowed-faction list and resets the faction
dropdown. A faction set before it would be discarded. A `FactionCouncils` option
rebuilds that list too. This is why every option is written before the faction is
picked. Difficulty is an index into the four start-screen levels. It is reported as the
campaign's own 1-4 numbering. The campaign reads the dropdown directly at launch. The
default-options pass the start button runs restores everything else from the last
recorded difficulty rather than from the control. The tutorial toggle is forced off
through its own handler. It defaults on for a player's first ever game. The tutorial
gates the map behind scripted steps no client can answer.

An `options` entry is a meta template dataName. The template carries the category it
belongs to. The wire format is names alone. The verb writes each one where the
picker's dropdown would have. An empty entry, a name matching no meta template, a
template that is not a new-campaign option, a category the scenario arg owns, and two
options in one category are each refused. The whole list is resolved before the
first option is written. A rejected list leaves the option map untouched. The
scenario arg is settled ahead of all of this. It stands whatever happens to the
options. `query.scenarios` lists every selectable option grouped by category.

Three of the menu's private members are read by reflection. The allowed-faction list
its dropdown handler indexes is what a faction name is matched against. The start
options map is reported back as the categories the launch will read. The scene
manager's absence means the menu never finished its own start. The controls the verb
sets and the methods it calls are public.

Launching reloads the scene. The verb returns the choices it made and leaves the
wait to the client, as `saves.load` does. It refuses while a campaign is loaded, when
the menu has not finished its own initialization, and while either the start screen's
or the load menu's loading screen is up. That last check is what stops a second launch.
A scene load takes tens of seconds and produces no campaign until it finishes. Every
other guard still passes. The loading screen each route raises is the only standing
record that one is already running.

## Prompts

A prompt in either of the active player's queues stops the simulation tick and pauses
time. Prompts belonging to other factions never block. The game's own prompt handler
answers them. It answers them only for AI factions. This is why the player's
queue accumulates instead.

`prompts.dismiss` takes two passes.

The screens pass repeats what the vanilla Autopilot does in a frame. This is the map of
every modal that can strand an unattended campaign. It handles the alert box (okay,
then close, then go-to, repeated while any is live, then the first live option button
on a notification that carries a choice). It handles the policy panel cancelled and
confirmed, the diplomatic response panel declined, an ally's war call declined, and a
faction greeting continued. It handles the diplomacy screen closed, an illegally-placed
army sent home, the research screen closed, and a trajectory change cancelled. Each is
guarded on its own so one failure does not stop the rest. The precombat screen is
deliberately absent. `combat.autoresolve` owns it and drives it a step per frame.

The prompt pass answers by name. It runs the player action the game's own AI path would
run. This includes a tech and a project chosen by the AI's selection strategies. It
includes councilor missions confirmed through the assignment screen's button. It
includes an unassigned org sold when the faction is over its org limit. Anything else
is reported as skipped with the reason.

A **narrative event** is answered by the SCREENS pass and **only** by it. The prompt
pass never selects an option for one.

An event is two independent queue entries:
`TIGlobalValuesState.TriggerNarrativeEvent` calls
`TINotificationQueueState.AlertNarrativeEvent` at `IL_0233` and
`TIPromptQueueState.AddPrompt` at `IL_0258`. Answering through the prompt queue runs
`SelectNarrativeEventOption`, whose `Execute` reaches `ExecuteNarrativeEventOption` and
`RemovePromptStatic` and touches the notification queue nowhere -- so the queued alert
still arrives, its option buttons are still live, and pressing one applies the choice a
second time: the effects, the costs, the org and project grants, all of it. It corrupts
the bookkeeping on the way through as well, since the box resolves its prompt with
`FindPromptForNarrativeEvent`, which by then finds nothing, so
`ExecuteNarrativeEventOption`'s closing `ClearNarrativeEvent(prompt)` at `IL_040a`
matches no entry, `RemoveAll` returns 0 rather than 1, and the engine logs "Error in
clearing narrative events" over a `pendingNarrativeEvents` entry that outlives the event.

The alert box is also the only path that runs the notification-side teardown --
`OnOptionButtonPressed`'s tail clears `receivingInputForNarrativeHotkeys`, drops the
resource listener, calls `CleanUp` and resumes the clock. A narrative prompt the prompt
pass meets before its box
has come up is reported as **skipped**, saying so; the screens pass takes it on a later
call. A `type`-filtered call skips the screens pass entirely, so it can never answer one.

The prompt pass does one thing to a narrative prompt, and it applies no option: a prompt
nothing can ever answer is dropped (`dropped: true`, with `deadEnd` saying which case it
was) rather than left to block the clock for the rest of the campaign. Two cases qualify,
and they are the engine's own condition from `HandleRespondToNarrativeEvent`: **no
narrative event template behind the prompt**, and **the event's target gone** -- null or deleted. The second
one is what the alert box turns on. `OnOptionButtonPressed` tests
`currentNarrativeEvent.selectedTarget` for null and for deleted and, on either, logs the
target away and skips the `StartAction` that is the only construction of
`SelectNarrativeEventOption`, while running its teardown regardless. So the press consumes
the box, the box does not return, and nothing is left that could answer the prompt. The
drop runs whichever way `narrative` is set, because it applies no option and so is not
answering a story event; `narrative: false` is the mode a caller is in while driving
`alert.choose` by hand, which is how the state is reached in the first place.

`alert.choose` reports the same thing from the other side, in its **`answered`** field,
which its verb row above spells out. A press whose option button is live but whose
controller is not yet taking narrative input is refused instead of made:
`receivingInputForNarrativeHotkeys` is set by a delayed coroutine, and a press ahead of
it is discarded silently.

Which button is the choice, and the rule is the engine's own:
`StratNarrativeResponseSelector`, the class `TIPromptQueueState`'s constructor installs,
weighing every valid option by its `baseAIPreference` and the faction's AI values, and
falling back to option 0 by itself when no option carries a weight -- so a single-option
acknowledgement answers 0 either way. The range it walks is **`numOptions`**, not
`eventOptions.Count`: 179 of the 260 shipped events declare fewer options than that list
holds (`event_Hurricane` is 2 against 4), and the popup builds its buttons from
`numOptions` as well. If the strategy throws or answers outside that range, the fallback
is the first option `NarrativeEventOption.ValidOption` accepts; if the pick is not a live
button, the fallback is the first live one. `pickedBy` says which rule produced it.

**Every narrative answer is reported**, because an unattended run that answers story
events silently is worse than one that stops.

`all` then drops whatever is still queued, except a narrative prompt. The decision behind
a dropped prompt goes unmade. This costs a research slot or a mission phase and leaves the
save intact. It is the difference between a run that continues and a run that sits paused
forever.

A narrative event is the exception because it has no forfeit. The alert and the prompt are
independent queue entries, `AlertNarrativeEvent` is called once at trigger time, and
nothing on the prompt side reaches back into the notification queue. `RemovePrompt` takes
the prompt half and leaves the box to arrive on schedule with its option buttons live, so
the choice is still applied, with its costs and grants. Dropping one hides a pending
decision rather than forfeiting it, so `all` reports it under **skipped** and leaves it for
the box. To take the decision yourself, use `narrative: false` and `alert.choose`.

Two consequences of that, worth stating because they are the opposite of what "drop"
sounds like, and both watched happen against a running game. A call that only drops --
`all: true` and nothing else -- still ANSWERS a story event, because the screens pass runs
first and `narrative` defaults true, and the answered event comes back in `dismissed`. And
`narrative: false` on the same call leaves an answerable one standing instead, which is the
only way to reach a drop pass without answering it. Both hold for an event offering at
least two options; a one-option event is pressed under every setting, so it demonstrates
neither.

An event offering ONE option is not a decision and is pressed in every mode. 63 of the 260
base-game events declare one option and 51 of those carry real effects, costs or grants, so
the press is reported like any other answer plus `single: true` and `optionDetail`, naming
what it applied. The count is `numOptions` clamped to `eventOptions`, never the number of
live buttons: the shipped list is padded past `numOptions` on most events, and every button
reads non-clickable during the engine's input-arming delay.

A prompt is reported under **`forced`** only when it actually left the two lists
the clock counts, and the measurement is `activePlayerNationPromptList` and
`activePlayerFactionPromptList`, not `RemovePrompt`'s return value.
`RemovePrompt` returns the MASTER list's result and discards the mirror's: it
touches the mirror only when the prompt's nation still has
`executiveFaction == activePlayer`, or when it has no executive faction and the
nation is gone. A nation handed to a different, non-null faction meets neither,
so the call returns true with the entry still blocking. One that did not leave
is reported under `skipped` with `stillBlocking` and the reason, so `remaining`
and this pass cannot disagree. The annotation lands on the entry belonging to
that prompt, located by prompt identity rather than by name: `Prompt` is a
struct with value equality over all five fields, and two nations can hold the
same prompt name at once.

The answer set covers three prompt types the engine's own prompt handler does not, since
an unhandled faction prompt is ignored in silence rather than dropped:

- **`PromptSelectSpaceCombatStance`**, queued by the precombat screen and served
  by the engine's handler to AI factions only, so the active player's copy sits
  there and holds the clock. The answer is Defend, through
  `PrecombatController.StanceSubmit`, which is the screen's own button path and
  what the vanilla Autopilot submits; `SelectCombatStance.Execute` removes the
  prompt itself, and the answer is measured against the active player's lists
  rather than assumed from the call. Three conditions gate it and each is
  reported as the skip reason instead: a live precombat controller with its
  canvas up; the autoresolve machine idle, since armed it submits the stance
  itself; and the screen showing the combat **this prompt** belongs to. The last
  one is not hypothetical: `SpaceCombatManager.CombatInit` queues the prompt with
  the new combat in `relatedGameState` whatever the screen is doing, while
  `PrecombatController.OnCombatInitiated` stashes the event in
  `delayedCombatInitiationEvent` and returns before `set_combat` whenever a
  post-combat report is still up, so the two diverge. Submitting on the screen's
  combat there would answer a different fight and leave this prompt blocking the
  clock, since `SelectCombatStance.Execute` removes the prompt keyed on its own
  combat. `combat.precombat action=close` closes the report and the screen then
  takes the new combat. Answering a stance also has a consequence one call
  later, on two conditions rather than one: `SpaceCombatManager.StanceSubmitted`
  returns at once unless `combatState.HaveStancesBeenSelected` is true, and then
  queues `PromptSelectSpaceCombatBid` on the combat's factions only when
  `combatState.requiresBidding` is true. So `remaining` non-zero straight after a
  successful answer is the bid, and `remaining` zero is a combat that needs no
  bid -- neither is a failed answer. `combat.stance` is the same submit with a
  stance of the caller's choosing.
- **`PromptBeginCombat`**, queued by `PrecombatController.OnCombatInitiated`, has
  no entry in the answer table and cannot have one: **there is no neutral answer
  to give it**. Every button that clears it commits an outcome -- close, cancel,
  reject, live -- and one of them is the accept `combat.autoresolve` owns and
  fires exactly once. So it is reported as skipped and `combat.precombat` is the
  contracted path. Every path off that screen removes it except
  `OnClosePostCombatButtonSelected`, which the autoresolve machine takes when
  the post-combat report is what is up. That is invisible on the ordinary path,
  where `OnAcceptAutoresolveSelected` already removed it, and strands the prompt
  on the path where the combat ended before simulation. The machine and
  `combat.precombat action=close` pair the removal with that button.
- **`PromptSelectTrajectory`**, queued by
  `OperationCanvasController.OpenThrustProfileTool` and removed by its private
  `CloseThrustProfileTool`. It records that a tool is open and forfeits no
  decision. The screens pass presses `changeTrajectoryCancelButton` when it is
  up; the answer pass adds the public `CloseActionPanel(true)`, which reaches
  the same engine teardown for the ordinary-targeting case where that button is
  not up, and drops the prompt directly only when neither path is on screen.

## Serialization rules

- Query verbs return curated, hand-built flat objects. Raw game objects are
  never fed to a general-purpose serializer. The state graph is cyclic and
  huge.
- Game-state references collapse to `{id, type, name}` everywhere. This includes
  inside `query.state`. The client walks the graph by issuing more queries.
- Newtonsoft (ships with the game) does the JSON encoding.

## Compatibility

Response fields may grow. Clients must tolerate unknown fields. All list responses
carry paging fields (`count`, `returned`, `truncated`) alongside the items.

The DLL is loaded into the game, so a rebuilt DLL reaches the bridge only on a
game restart. `version` reports which one is answering. A client's own staleness
is invisible on the wire and is the client's to report.
